## C. 보존할 강점

- 정적 사이트라 공격 표면과 실행 복잡성이 작고, 첫 응답이 빠름.
- `lang="ko"`, 건너뛰기 링크, 의미 있는 제목 구조, `:focus-visible`, 움직임 축소 설정 등 접근성 기초가 이미 있음.
- Iruvy 로고, 사용자 앱과 관리자 앱 화면, 홍보 영상과 포스터 등 실제 제품 자산이 있음.
- 문제, 제품, 실증, 도입 순서가 기본적으로 존재하며 기관 구매자 중심 메시지가 이미 시작되어 있음.
- 관계 유형을 `도입`, `PoC`, `지원`, `협의`, `육성`, `검증`으로 구분하려는 의도가 있음.
- 개인정보 처리방침, 사이트맵, 로봇 설정, 공유 미리보기의 최소 기반이 있음.
- CSS 사용자 정의 속성으로 핵심 색상이 어느 정도 중앙 관리됨.

## D. 약점

### 제품과 메시지

- 홈페이지 첫 문구가 추상적인 비전인 “누구나 어디든 갈 수 있는 세상”에 머물며, 제품을 한 번에 설명하는 구체성이 부족함.
- 제품, 솔루션, 기술, 실증, 회사 정보를 한 페이지에 압축하여 기술 검토자와 기관 담당자가 깊이 확인할 경로가 없음.
- 기술 구역이 “사람을 안내하면서 공간을 데이터로 만듭니다”라고 시작해 개인정보 우려를 만들고 핵심 가치의 우선순위를 흐림.
- `mailto:`만 있어 도입 검토에 필요한 시설 유형, 규모, 일정, 문제를 구조적으로 받지 못함.

### 근거와 신뢰

- `26.6% → 96.7%`, `90명(반복 실증)`, `약 300m` 수치는 웹사이트 외부의 원자료나 보고서와 연결되지 않음.
- “서울 AI스마트시티재단 도입”은 현재 확인 가능한 장기 메모상 “도입 관심과 구체 자료 요청”보다 강한 표현으로, 과장 위험이 있음.
- 기존 앱 화면 내부에 이전 제품명 `Riav`가 남아 브랜드 일관성이 깨짐.
- 기존 공유 이미지에는 `Iruvy`, `Riav`가 남아 현재 브랜드와 불일치함.
- `hero-cover.png`는 제품 사용 장면을 잘 설명하지만 합성 이미지로 보이며 실제 현장 실증 사진처럼 오인될 수 있으므로 설명 없이 근거 구역에 사용하면 안 됨.

### 구조와 유지보수

- 모든 홈페이지 콘텐츠와 구성 요소가 하나의 372줄 HTML에 직접 작성됨.
- 1,264줄 단일 CSS 파일에 페이지, 구성 요소, 반응형 규칙이 섞여 있음.
- 빌드, 정적 검사, 링크 검사, HTML 검증, 자동 접근성 검사, 회귀 검사가 없음.
- 로컬 OTF 5개를 보유하지만 외부 CDN과 구글 글꼴을 다시 불러와 개인정보, 가용성, 성능 측면에서 불필요한 외부 의존성이 생김.
- 사용 여부가 불분명한 큰 PNG, 이전 이름이 남은 이미지, 문서 산출물이 사이트 자산과 섞여 있음.

### 접근성과 반응형

- 모바일 메뉴가 `details` 기반이라 기본 조작은 가능하지만 열린 상태의 명확한 시각 피드백과 메뉴 선택 후 닫힘 처리가 부족함.
- 보조 페이지 머리글의 `nav`는 모바일 전용 처리 없이 공용 스타일에 의존함.
- 실제 동작하는 문의 양식과 오류·성공 상태가 없음.
- 앱 화면 속 작은 글자는 대체 설명만으로 모든 정보를 전달하지 못함.
- 일부 연한 회색 문구와 보라색 조합은 최종 대비 수치 검증이 필요함.

### 검색과 공유

- 홈페이지 외 고유 경로가 지원과 개인정보뿐임.
- 구조화 데이터, 접근성 선언, 제품·솔루션·기술·실증별 메타데이터가 없음.
- 공유 이미지가 현재 브랜드와 다름.
- 사이트맵의 최종 변경일이 실제 운영 갱신과 일치하지 않음.

## E. 위험

- 미추적 `deliverables/*.docx`, `deliverables/*.pdf`는 사용자 작업물이므로 이동·삭제·덮어쓰기를 금지함.
- 운영 배포가 저장소 루트를 직접 제공하므로 경로 변경 시 기존 링크가 깨질 수 있음.
- 실증 수치와 기관 관계를 근거 없이 강화하면 투자·영업 신뢰를 훼손할 수 있음.
- 앱 화면을 새 브랜드로 보이게 임의 변조하면 실제 제품 상태를 왜곡할 수 있음. 화면은 제품의 해당 시점 시제품임을 밝히거나 최신 캡처로 교체해야 함.
- 새 문의 기반 서비스가 없으므로 양식 제출 성공을 가장하면 안 됨.
- 정적 사이트를 대형 프레임워크로 바꾸면 배포 복잡성과 자바스크립트 비용이 제품 가치보다 커질 수 있음.

## F. 제안 구조

현재 배포 장점을 유지한 다중 경로 정적 사이트로 개편함.

```text
website/
├─ index.html
├─ product/index.html
├─ solutions/index.html
├─ technology/index.html
├─ proof/index.html
├─ company/index.html
├─ contact/index.html
├─ privacy/index.html
├─ accessibility/index.html
├─ assets/
│  ├─ brand/
│  ├─ product/
│  ├─ proof/
│  ├─ media/
│  └─ fonts/
├─ styles/
│  ├─ tokens.css
│  ├─ base.css
│  ├─ components.css
│  └─ pages.css
├─ scripts/site.js
├─ tests/
├─ docs/
└─ package.json
```

선택 이유:

- 서버 렌더링이나 데이터베이스가 필요 없는 소개 사이트이므로 정적 HTML의 속도와 안정성을 유지함.
- 정보 목적별 경로를 만들어 기관 구매자와 기술 검토자의 탐색 깊이를 확보함.
- 공통 토큰, 기본 규칙, 구성 요소, 페이지 스타일을 분리하여 단일 CSS 비대화를 줄임.
- 필요한 상호작용만 작은 공용 스크립트에 두어 자바스크립트 비용을 제한함.
- 의존성 없는 검사 도구를 우선 추가하여 배포 구조를 바꾸지 않고 품질 기준을 만듦.

## 감사 결론

현재 사이트는 기능적으로 안전한 소개 초안이지만 “프리미엄 기관용 홍보 사이트” 기준에는 메시지 깊이, 브랜드 일관성, 근거 투명성, 전환 경로, 페이지 구조, 검증 체계가 부족함. 정적 배포 방식은 보존하되 정보 구조와 시각 체계는 전면 재구성하는 것이 가장 위험 대비 효과가 큼.
