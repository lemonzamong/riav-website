# Content Strategy

원칙: 모든 섹션은 목적을 가진다. 청중은 **챔피언**, 언어는 명확·구체·근거 기반. 기존 `docs/content-strategy.md`(수치 등급) + 이 문서.

## 섹션 설계 규격 (각 섹션마다)

청중 · 사용자 질문 · 섹션 목표 · 헤드라인 · 보조 메시지 · 근거 · 시각 · CTA · 접근성 고려.

## 이해를 위한 글쓰기 (§9.1)

- 금지: 모호한 슬로건, 기업 상투어, 근거 없는 최상급, 과도한 전문용어, 긴 추상 문장, 버즈워드 반복, 관련성보다 앞선 기술 상세.
- 구체 문장:
  - 나쁨: "포용적 공간 지능을 AI로 혁신합니다."
  - 좋음: "방문객이 목적지를 고르면 음성·진동·화면으로 다음 행동을 안내합니다."

## 주장 상태 라벨 (§9.2)

모든 주장을 Proven/Supported/Plausible/Aspirational로 내부 분류(`docs/EVIDENCE.md`). Aspirational을 사실처럼 게시 금지. 수치엔 항상 n·과제·장소·"팀 제공·제삼자 인증 아님·특정 환경".

## 구매자 페이지에서 배제 (§9.3)

로봇 학습·피지컬 AI 데이터 시장·데이터 무어·투자자용 시장 확장 서사 → 회사/비전 페이지 장기 관점으로만. 구매자를 접근성 결과에서 이탈시키지 않음.

## 페이지별 콘텐츠 목표

| 페이지 | 청중 질문 | 콘텐츠 목표 | 핵심 CTA |
|---|---|---|---|
| 홈 | 이게 뭐고 우리 기관에 왜 필요? | 챔피언 무장(문제→결과→근거→레퍼런스→진입) | 무료/Light PoC 문의 |
| 제품 | 사용자·운영자가 실제로 뭘 하나 | 경험 흐름·다중감각·운영 도구 | PoC 문의 |
| 솔루션 | 우리 시설엔 어떻게? | 시설별 도입 이유·지표 | 시설별 문의 |
| 기술 | 어떻게 작동·프라이버시·부담? | 신호 위계·단계 도입·프라이버시 | 기술 검토 요청 |
| 실증 | 진짜 되나? | 수치·방법·제한·관계 정직 | PoC 설계 문의 |
| 회사 | 믿을 만한가·장기 방향? | 팀·문제의식·비전(장기 서사 여기) | 대화 시작 |
| 문의 | 어떻게 시작? | 낮은 마찰·mailto 인계 | 제출 |

## 톤·표기

- 지원서/제안서형이 아닌 **웹 카피** — 짧고 스캔 가능. 결론형 헤드라인.
- 영어 eyebrow 라벨은 장식 최소화·의미 점검(기관 구매자 가독성).
- 마무리에 감정 한 줄 허용(1차 리드는 구매자 결과).

## 후속 콘텐츠 갭

- 조달청 혁신제품·무과실 경로 안내.
- 프라이버시(위치정보) 답변 강화 카피.
- 다운로드형 조달 킷(원페이지·PoC 제안서) 게시.
- 하위 페이지 카피의 결과·구매자 관점 강화.
